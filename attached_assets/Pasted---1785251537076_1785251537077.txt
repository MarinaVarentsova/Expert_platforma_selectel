Проведи полный технический аудит загрузки и просмотра файлов, прикреплённых заказчиком к заказу.

Пока ничего не меняй.
Не делай commit.
Не трогай production.

Контекст:

Заказчик при создании или редактировании заказа может прикрепить файл.

Нужно точно понять:

- куда сейчас загружается файл;
- где он физически хранится;
- что записывается в БД;
- как файл связан с заказом;
- доступен ли этот файл эксперту;
- через какой интерфейс и endpoint эксперт его открывает или скачивает;
- безопасно ли устроено разграничение доступа.

Проведи аудит всей цепочки.

1. Frontend загрузки

Найди все места, где заказчик может прикрепить файл к заказу:

- создание новой заявки;
- редактирование заявки;
- страница заказа;
- дополнительные материалы;
- другие формы, если есть.

Для каждого места покажи:

- файл;
- компонент;
- функцию;
- endpoint;
- HTTP method;
- Content-Type;
- отправляется сам файл или только метаданные/URL;
- передаётся ли Authorization;
- передаётся ли request_id;
- ограничения по размеру;
- разрешённые типы файлов;
- поддерживается ли загрузка нескольких файлов.

2. Backend

Найди все backend-маршруты, связанные с файлами заказа, например:

- /api/palata/request-files;
- /api/palata/requests/:id/files;
- upload;
- download;
- attachments;
- materials;
- storage.

Для каждого endpoint покажи:

- маршрут;
- метод;
- handler;
- входные данные;
- проверку токена;
- проверку роли;
- проверку принадлежности заказа пользователю;
- ответ сервера;
- возможные ошибки.

3. Физическое хранилище

Точно определить, куда записывается бинарный файл:

- локальный диск контейнера;
- Selectel S3;
- Supabase Storage;
- PostgreSQL;
- внешний URL;
- base64 в БД;
- другое место.

Покажи:

- используемые переменные окружения;
- имя bucket;
- путь или key объекта;
- формирование имени файла;
- сохраняется ли оригинальное имя;
- что произойдёт с файлами после redeploy контейнера.

Не выводить реальные секреты и ключи.

4. База данных

Найди таблицу для прикреплённых файлов.

Верни:

- название таблицы;
- структуру используемых колонок;
- request_id;
- uploader/customer_id;
- file_name;
- storage key;
- URL;
- MIME type;
- размер;
- created_at;
- status или deleted_at, если есть.

Покажи SQL или код INSERT при загрузке и SELECT при чтении.

5. Связь файла с заказом

Проверить:

- является ли request_id обязательным;
- существует ли внешний ключ;
- может ли файл оказаться без заказа;
- может ли файл ошибочно прикрепиться к чужому заказу;
- удаляется ли файл при удалении или отмене заказа;
- остаются ли потерянные файлы.

6. Доступ заказчика

Проверить:

- где заказчик видит прикреплённые файлы;
- может ли скачать;
- может ли удалить;
- может ли заменить;
- проверяется ли, что заказ принадлежит этому заказчику.

7. Доступ эксперта

Это главная часть аудита.

Проверить:

- где на странице RequestDetail эксперт должен видеть материалы заказа;
- какой frontend-запрос получает список файлов;
- какой endpoint используется;
- передаётся ли Authorization;
- проверяет ли backend, что эксперт:
  - назначен на этот заказ;
  - участвует в подборе;
  - выбран заказчиком;
  - либо имеет другой допустимый статус;
- может ли посторонний эксперт получить файлы, зная request_id;
- может ли эксперт открыть или скачать сам бинарный файл;
- является ли ссылка публичной;
- истекает ли ссылка;
- подписанная ли это ссылка.

8. Проверить существующую реализацию RequestDetail

Найти блоки:

- «Подробнее о заказе»;
- «Материалы»;
- «Файлы»;
- «Документы»;
- «Вложения».

Показать:

- откуда берутся данные;
- почему файл может отображаться или не отображаться;
- каким способом открывается;
- есть ли кнопка просмотра или скачивания;
- что увидит эксперт, если файл недоступен.

9. Безопасность

Проверить следующие риски:

- endpoint файлов публичный;
- отсутствие проверки Authorization;
- отсутствие проверки request_id и пользователя;
- возможность перебора UUID;
- публичный постоянный URL;
- возможность загрузить исполняемый файл;
- отсутствие лимита размера;
- подмена MIME type;
- path traversal через имя файла;
- XSS через имя файла;
- хранение файлов на временном диске контейнера;
- утечка персональных данных через публичный bucket;
- доступ эксперта к файлам чужого заказа.

10. Production-конфигурация

Проверить код и конфигурацию проекта:

- какие storage-переменные ожидаются;
- какие из них обязательны;
- имеется ли fallback;
- что происходит, если storage не настроен;
- не используется ли до сих пор старый Supabase Storage после переезда на Selectel.

Не выводить значения переменных и секретов.

11. Практический сценарий

Проследить один файл от начала до конца:

1. Заказчик выбирает файл.
2. Нажимает создание или сохранение заказа.
3. Frontend отправляет запрос.
4. Backend принимает данные.
5. Файл записывается в хранилище.
6. Метаданные записываются в БД.
7. Эксперт открывает заказ.
8. Frontend получает список файлов.
9. Эксперт нажимает файл.
10. Backend или storage отдаёт содержимое.

Для каждого шага указать конкретный файл кода, функцию и endpoint.

12. Итоговый отчёт

Верни отчёт в структуре:

А. Текущая архитектура загрузки файлов.
Б. Где физически лежат файлы.
В. Что хранится в БД.
Г. Как заказчик получает доступ.
Д. Как эксперт получает доступ.
Е. Какие проверки прав существуют.
Ж. Найденные проблемы и риски.
З. Ответ на главный вопрос:

«Может ли заказчик сейчас прикрепить файл к заказу, и доступен ли этот файл для просмотра или скачивания выбранному эксперту?»

И. Минимальный план исправления, если цепочка не работает или небезопасна.

Не создавать миграции.
