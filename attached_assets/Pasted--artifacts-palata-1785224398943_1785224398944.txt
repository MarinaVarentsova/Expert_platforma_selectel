Аудит принят. Теперь подготовь точечное исправление защиты от устаревших действий в artifacts/palata/server.js.

Перед изменениями сначала покажи план и точный diff. Не делай commit, пока не завершишь проверки.

Контекст подтверждённого дефекта:

- palata_requests.status уже находился в in_work;
- palata_request_matches.status назначенного эксперта был accepted_work;
- устаревшая кнопка «Отказаться» вызвала handleDeclineRequest;
- backend без проверки изменил статус матча accepted_work → declined;
- основной заказ мог остаться in_work, но интерфейс переместил карточку эксперта в «Отказ».

Нужно исправить класс ошибок со старыми, не обновлёнными страницами.

ТРЕБОВАНИЯ

1. Все проверки выполнять на backend по актуальным данным PostgreSQL Selectel.
2. Проверка и UPDATE должны выполняться внутри одной транзакции.
3. При загрузке заказа использовать блокировку строки:
   SELECT ... FROM public.palata_requests
   WHERE id = $1
   FOR UPDATE;
4. Не полагаться на состояние frontend.
5. При конфликте возвращать HTTP 409:

{
  "success": false,
  "code": "REQUEST_STATUS_CONFLICT",
  "freshStatus": "<актуальный статус>",
  "error": "Заказ уже в работе"
}

Для completed/cancelled использовать сообщение:
«Действие больше недоступно, статус заказа изменился. Обновите страницу».

6. Не создавать единственный общий список TERMINAL для всех действий.
Для каждого действия определить собственные допустимые исходные статусы заказа и матча.

ПРОВЕРКИ ПО ДЕЙСТВИЯМ

A. handleDeclineRequest — «Отказаться»

Обязательно:
- загрузить актуальный palata_requests.status;
- загрузить актуальный palata_request_matches.status;
- запретить отказ, если заказ уже in_work, completed или cancelled;
- запретить отказ, если матч уже:
  accepted_work,
  completed,
  closed_by_other_expert,
  declined;
- в самом UPDATE добавить условие по допустимому текущему статусу;
- проверить rowCount;
- если rowCount = 0, сделать ROLLBACK и вернуть HTTP 409 с кодом MATCH_ALREADY_RESOLVED.

Главная гарантия:
accepted_work → declined должен быть невозможен при любом запросе, включая запрос со старой страницы.

B. handleTakeWork — «ОК, беру в работу»

- запретить повторное действие, если заказ уже in_work, completed или cancelled;
- проверить, что действие выполняет именно эксперт соответствующего матча;
- проверить допустимый исходный статус матча;
- обеспечить атомарность выбора эксперта и закрытия остальных матчей.

C. handleExpertCanStart и handleApplyMarket — «Предложить дату»

- запретить действие при in_work, completed, cancelled;
- не создавать новые action items по закрытому или уже выполняемому заказу.

D. handleApprovStartDate и handleDeclineStartDate —
«Согласовать дату» / «Отклонить дату»

- сохранить существующие проверки в approve;
- добавить такую же жёсткую серверную проверку в decline;
- при in_work возвращать HTTP 409, а не создавать новые action items;
- резолвить переданный устаревший action item, если он существует и принадлежит этому заказу и пользователю.

E. handleCompleteWork — «Завершить работу»

- разрешать только если:
  palata_requests.status = in_work;
  assigned_expert_id совпадает с текущим экспертом;
  статус его матча = accepted_work;
- повторное завершение completed должно возвращать 409 или безопасный идемпотентный ответ без повторных action items.

F. handleCustomerComplete — «Работа выполнена»

- разрешать только владельцу заказа;
- только из допустимого состояния in_work;
- повторный completed не должен создавать повторные события.

G. handleCustomerCancel — «Сделать неактуальным»

- разрешать только до начала выполнения;
- запретить при in_work и completed;
- cancelled обрабатывать идемпотентно либо возвращать 409;
- сохранить закрытие открытых action items.

ACTION ITEMS

После перехода заказа в in_work:
- отменить все открытые action items этого request_id, кроме уже резолвленного текущего действия;
- не позволять никакому endpoint после этого создавать:
  expert_can_start_from,
  customer_selected_you,
  you_are_approved_for_work,
  choose_another_expert.

После completed или cancelled:
- закрыть все оставшиеся открытые action items заказа.

Проверять actionItemId:
- action item существует;
- относится к request_id;
- назначен текущему пользователю;
- ещё не resolved/cancelled;
- его тип подходит для выполняемого действия.

FRONTEND

Не использовать frontend как единственную защиту.
Но проверить обработку HTTP 409:

- показывать текст error из backend;
- затем обновлять данные заказа;
- не оставлять старую карточку и активную кнопку на экране.

Если общий обработчик 409 уже существует — использовать его.
Не переписывать интерфейс.
