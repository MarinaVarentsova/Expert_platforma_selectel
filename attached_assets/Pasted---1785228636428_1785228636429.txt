Реализуй временное исправление обработки истёкшей сессии в приложении Палаты.

Контекст аудита:

- используется только access token;
- токен хранится в localStorage под ключом palata_access_token;
- refresh token отсутствует;
- после истечения токена защищённые endpoint возвращают:
  HTTP 401
  { "error": "INVALID_TOKEN" }
- frontend продолжает считать пользователя авторизованным;
- пользователь видит ошибки загрузки и вынужден вручную выходить и входить заново.

Нужно реализовать временное решение без изменения Auth Service и без refresh token.

ОЖИДАЕМОЕ ПОВЕДЕНИЕ

При первом ответе HTTP 401 от любого запроса к /api/palata/*:

1. удалить palata_access_token из localStorage;
2. перевести AuthContext в unauthenticated;
3. показать пользователю сообщение:
   «Сессия завершена. Войдите снова.»
4. перенаправить пользователя на /login;
5. не оставлять пользователя на сломанной странице;
6. не создавать цикл редиректов;
7. не показывать десятки одинаковых сообщений, если несколько запросов одновременно получили 401.

После перехода на /login пользователь сразу вводит логин и пароль повторно.

ТРЕБОВАНИЯ К РЕАЛИЗАЦИИ

1. Сначала найди наиболее общий и минимальный способ обработки 401.

2. Не переписывай все примерно 128 fetch-вызовов вручную, если можно:
   - добавить общий обработчик;
   - создать минимальный auth-aware fetch wrapper;
   - либо использовать глобальное событие истечения сессии.

3. Предпочтительная минимальная схема:

- создать функцию handleExpiredSession(), которая:
  - выполняется только один раз одновременно;
  - вызывает clearToken();
  - уведомляет AuthContext о завершении сессии;
  - сохраняет сообщение для страницы входа;
  - выполняет переход на /login.

- создать функцию palataFetch(input, init), которая вызывает fetch и:
  - при response.status === 401;
  - только для запросов /api/palata/*;
  - вызывает handleExpiredSession();
  - возвращает исходный Response без повторного запроса.

4. Подключить palataFetch к основным общим местам загрузки данных:
   - requests/expert/matches;
   - action-items/me;
   - requests/customer;
   - profiles;
   - детали заказа;
   - остальные общие функции API.

5. Если в проекте невозможно безопасно заменить все вызовы сейчас, предложи и реализуй минимальный глобальный механизм:
   - backend 401 должен приводить к единому browser event;
   - AuthProvider слушает событие;
   - очищает токен и состояние;
   - выполняет переход на /login.

6. На странице входа показать одно сообщение:

«Сессия завершена. Войдите снова.»

Сообщение можно передать через:
- router state;
- sessionStorage;
- query-параметр;
но оно не должно отображаться повторно после следующего успешного входа.

7. Не перенаправлять на login при:
- 401 от самого /api/auth/login;
- неверном пароле;
- публичных страницах;
- запросах регистрации или восстановления пароля.

8. Не логировать токены.

9. Не изменять:
- внешний Auth Service;
- backend server.js;
- схему БД;
- роли;
- логику входа;
- бизнес-логику заказов.

10. Защита от параллельных 401:
если одновременно получили 401 несколько запросов, очистка и редирект должны выполниться только один раз.

ТЕСТЫ

Проверь:

1. Действующий токен:
   кабинет и запросы работают без изменений.

2. Просроченный/невалидный токен:
   первый запрос к /api/palata/* получает 401;
   токен удаляется;
   пользователь переводится на /login;
   появляется сообщение «Сессия завершена. Войдите снова.»

3. Пять параллельных запросов с невалидным токеном:
   только один редирект;
   только одно сообщение.

4. Неверный пароль при login:
   остаётся обычная ошибка входа;
   сообщение о завершении сессии не появляется.

5. После повторного успешного входа:
   сообщение исчезает;
   кабинет загружается нормально.
