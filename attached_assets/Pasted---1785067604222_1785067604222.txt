Нужно исправить только открытие страницы заказа в личном кабинете заказчика.

Фактическая ситуация:

1. Заказ успешно создаётся.
2. Заказ отображается в канбане заказчика.
3. Эксперт видит этот же заказ на рынке и может раскрыть его.
4. Но при переходе заказчика по адресу:

/requests/d4172d25-6458-4ca3-93ea-6b672c564447

frontend вызывает:

GET /api/palata/requests/d4172d25-6458-4ca3-93ea-6b672c564447/detail

и получает HTTP 500:

QUERY_FAILED

В консоли также есть отдельный 404 /api/notify, но его сейчас не исправлять — он не должен мешать загрузке заказа.

Сделай точечную диагностику и исправление customer detail endpoint.

Этап 1. Найти фактический маршрут

1. Найди в production server-side коде обработчик:

GET /api/palata/requests/:id/detail

или эквивалентный маршрут, который возвращает данные заказа заказчику.

2. Покажи:

- файл;
- номер строки;
- полный SQL-запрос;
- параметры SQL;
- таблицы и поля, используемые в запросе;
- проверки авторизации и владельца заказа.

3. Найди место, где клиенту возвращается:

QUERY_FAILED

4. До исправления добавь безопасное серверное логирование реальной ошибки PostgreSQL:

console.error("[REQUEST-DETAIL] query failed", {
  requestId,
  userId,
  code: error.code,
  message: error.message,
  detail: error.detail,
  hint: error.hint
});

Не логировать:

- JWT;
- Authorization;
- пароли;
- секреты;
- токены;
- строки подключения.

Этап 2. Проверить существующий заказ

Для UUID:

d4172d25-6458-4ca3-93ea-6b672c564447

проверь запросом к базе:

SELECT *
FROM palata_requests
WHERE id = 'd4172d25-6458-4ca3-93ea-6b672c564447';

Также проверь фактическое поле владельца заказа и его значение.

Текущий авторизованный заказчик:

user_id = d715c0e0-5b18-403c-b0e2-b7cf57b11860

email = analitikba02@gmail.com

Не предполагай имя поля владельца. Определи его по фактической схеме таблицы palata_requests.

Этап 3. Сравнить с рабочим expert endpoint

1. Найди серверный запрос, который успешно отдаёт этот заказ эксперту на рынке.

2. Сравни его с customer detail endpoint:

- имя основной таблицы;
- поля направления;
- поля региона;
- join с направлениями;
- join с регионами;
- join с заказчиком;
- join с matches;
- join с expert profiles;
- названия колонок;
- типы UUID.

3. Если customer endpoint использует несуществующую колонку, старое имя таблицы, неправильный JOIN или устаревшую схему — исправь его по фактической текущей схеме базы.

Этап 4. Требуемое безопасное поведение

Маршрут должен:

1. Проверить авторизацию.
2. Получить userId авторизованного заказчика.
3. Найти заказ по UUID.
4. Убедиться, что заказ принадлежит этому заказчику.
5. Вернуть HTTP 404, если заказа нет.
6. Вернуть HTTP 403, если заказ принадлежит другому заказчику.
7. Вернуть HTTP 200 с данными заказа, если заказ найден и принадлежит текущему пользователю.
8. Не возвращать QUERY_FAILED при обычном отсутствии данных в связанных таблицах.
9. Не использовать INNER JOIN для необязательных связанных сущностей, если из-за отсутствия записи исчезает основной заказ. Для необязательных данных использовать LEFT JOIN либо отдельные запросы.
10. Не менять формат ответа, который ожидает текущая frontend-страница, без необходимости.

Особенно проверь необязательные связи:

- palata_request_matches;
- эксперт;
- сертификаты;
- отклики;
- назначения;
- регион;
- направление.

Новый заказ может ещё не иметь части этих записей. Их отсутствие не должно вызывать 500.

Этап 5. Не изменять

Не менять:

- создание заказа;
- AI-определение направления;
- AI Gateway;
- endpoint рынка экспертов;
- канбан;
- статусы заказа;
- схему БД без доказанной необходимости;
- frontend-дизайн;
- auth service;
- /api/notify.

Не добавлять миграцию наугад.

1. Выполни node --check изменённого серверного файла.
2. Выполни существующую сборку проекта Палаты.
3. Проверь customer detail endpoint локально или доступным integration-тестом для:

d4172d25-6458-4ca3-93ea-6b672c564447

userId:
d715c0e0-5b18-403c-b0e2-b7cf57b11860

4. Ожидаемый результат:

HTTP 200

и данные заказа.

5. Повторно проверь поиск по коду и убедись, что endpoint рынка экспертов не изменён.

6. Сделай один commit:

fix: load customer request detail

7. Сделай push в ту же ветку main, которую разворачивает Coolify.

В конце покажи:

- точную причину QUERY_FAILED;
- файл и строку;
